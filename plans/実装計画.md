# オフライン地図 PWA 実装計画

## 1. この文書の目的

本書は [`plans/要件.md`](./要件.md) に定義された初期MVPを、実装担当者による解釈差が生じない粒度まで具体化した実装手順である。

本書に従う実装では、経路検索、地名・住所・POI検索、ユーザーアカウント、クラウド同期、位置履歴、バックグラウンド位置追跡、オフラインルーティング、ベクタータイル生成、複数タイルソース、GPX、GeoJSON、E2Eテストを追加しない。

## 2. 実装前提と固定する判断

現時点のリポジトリには要件書以外の実装がないため、以下を初期実装の確定事項とする。

| 項目 | 初期実装で採用する内容 |
| --- | --- |
| パッケージ管理 | npm |
| アプリ基盤 | Vite + React + TypeScript、TypeScript strict mode |
| 地図 | MapLibre GL JSのRaster Source/Layer |
| 状態管理 | Zustand。用途別Storeに分割する |
| HTTP補助 | SWR。ただし地図タイル取得には使用しない |
| ルーティング | wouter |
| 永続データ検証 | `zod/mini` |
| タイルバイナリ | OPFSの `/tiles/{source}/{z}/{x}/{y}.png` |
| 構造化メタデータ | ネイティブIndexedDBを薄いPromise wrapper経由で使用 |
| PWA | `vite-plugin-pwa` を使用し、生成されるService WorkerでApp Shellをprecache |
| 初期タイルソース | 国土地理院標準地図 `std` のみ |
| 初期表示 | 日本全体が見える中心 `[138, 37]`、zoom 5、bearing 0、pitch 0 |
| MapLibre独自scheme | `opfs-gsi://{source}/{z}/{x}/{y}` |
| 再検証間隔 | 24時間 |
| 明示ダウンロード同時数 | 6 |
| 通常キャッシュ上限 | `min(512 MiB, quota * 0.2)`。quota不明時は512 MiB |
| ダウンロード容量推定 | 実績がなければ1タイル20 KiB。取得済みタイルのsource別平均を優先 |
| OfflineArea指定範囲 | 保存操作時の現在のMapLibre表示bounds |
| OfflineArea zoom | フォームで整数のmin/maxを指定。初期値は現在zoomのfloor値からsource maxZoomまでではなく、通信量を抑えるため `floor(currentZoom)` から `min(floor(currentZoom) + 2, source.maxZoom)` |
| OfflineArea削除 | 参照とpinを解除し、タイル本体は通常キャッシュへ降格。即時物理削除しない |
| Worker | MVPでは導入しない。純粋計算・I/OをUIから分離し、計測後に移せる形に留める |
| E2E | 導入しない |

`TileMetadata.pinned` は高速な一覧・GC判定のため保持する非正規化値とし、真偽の正本は `offlineAreaTiles` に存在する参照の有無とする。要件書中の単一 `downloadAreaId` は使用しない。

ブラウザーがOPFSに非対応の場合、地図のオンライン表示は継続できるようにネットワーク取得結果をMapLibreへ返すが、永続キャッシュ、オフラインエリア保存、キャッシュ削除・容量内訳は利用不可としてUIで明示する。Cache Storageをタイル保存の代替にはしない。

## 3. 完成条件

以下をすべて満たした時点をMVP完成とする。

1. オンライン初回表示で地理院標準地図を表示し、取得タイルをOPFSとIndexedDBへ保存できる。
2. 再読み込み後、保存済みタイルはネットワーク応答を待たずに表示される。
3. オフライン時は保存済みタイルだけを表示し、未保存タイルの失敗でアプリ全体が停止しない。
4. 24時間以上未確認のローカルタイルは表示後に条件付き再検証され、失敗しても既存ファイルを維持する。
5. 現在地ボタンから権限を要求し、位置、精度円、利用可能なheadingを地図に表示できる。
6. ユーザー操作から方角権限を要求し、端末方位またはGPS headingを表示できる。
7. 現在の表示範囲とzoom範囲を確認してOfflineAreaを作成し、進捗表示、一時停止、再開、更新、削除ができる。
8. 複数OfflineAreaが同じタイルを参照しても、一方の削除で他方のpinが解除されない。
9. 通常キャッシュのみがLRU GCおよび「キャッシュを削除」の対象となる。
10. App ShellがService Workerによりオフライン起動でき、manifestからインストール可能である。
11. 対象ブラウザーAPIはすべてfeature detectionされ、非対応・拒否・失敗状態が日本語UIに反映される。
12. `npm run test:run`、`npm run lint`、`npm run format:check`、`npm run build` が成功する。

## 7. タイルソースと座標計算

### 7.1 タイルソース

`src/map/tileSources.ts` に `std` の定義を置く。

```ts
interface MapTileSource {
  id: TileSourceId;
  name: string;
  minZoom: number;
  maxZoom: number;
  extension: "png";
  contentTypes: readonly string[];
  getRemoteUrl(tile: TileCoordinate): string;
  attribution: string;
}
```

- URLは `https://cyberjapandata.gsi.go.jp/xyz/std/{z}/{x}/{y}.png`。
- zoomは標準地図の利用可能範囲として0〜18に固定する。
- attributionは地図上に常時表示し、リンク先を国土地理院の利用規約またはタイル説明ページとする。
- remote URLを組み立てる前に整数、zoom範囲、`0 <= x,y < 2**z` を検証する。

### 7.2 `tileKey.ts`

- `createTileKey(coordinate)` は `std/15/29091/12903` 形式を返す。
- `parseTileKey(unknown)` はzod/miniで外部・永続化入力を検証後、座標範囲も検査する。
- OPFS pathはキー文字列の直接連結ではなく、検証済み座標からpath segmentを作る。path traversal文字列を受け付けない。

### 7.3 `tileMath.ts`

純粋関数として次を実装する。

- longitudeを `[-180, 180]` に正規化する。
- latitudeをWeb Mercator限界 `[-85.05112878, 85.05112878]` にclampする。
- 緯度経度からXYZのx/yをfloorで計算し、範囲内へclampする。
- boundsのnorth-westとsouth-eastからzoomごとのinclusiveなx/y範囲を列挙する。
- `west <= east` は通常列挙、`west > east` は日付変更線を跨ぐため `[west, 180]` と `[-180, east]` に分割する。
- minZoomからmaxZoomまで昇順、各zoom内はy昇順・x昇順で安定した順序にする。
- 境界上の重複と分割時の重複を `TileKey` で除去する。
- `countTilesForBounds` は巨大配列を作らず同じ規則で枚数を計算する。確認Dialog表示はこの関数を使う。

テストでは東京付近、世界全体、Mercator限界、日付変更線、zoom単一/複数、不正なzoom範囲を固定値で検証する。

## 8. IndexedDB設計

### 8.1 DBとStore

DB名は `offline-map`、初期versionは1とする。`onupgradeneeded` 以外でschema変更を行わない。

| Store | keyPath | Index |
| --- | --- | --- |
| `tiles` | `key` | `byLastAccessed` = `lastAccessedAt`、`bySource` = `source` |
| `offlineAreas` | `id` | `byCreatedAt` = `createdAt` |
| `offlineAreaTiles` | `[areaId, tileKey]` | `byAreaId` = `areaId`、`byTileKey` = `tileKey` |
| `downloadJobs` | `[areaId, tileKey]` | `byAreaState` = `[areaId, state]` |
| `settings` | `key` | なし |

`settings` には少なくとも `cacheLimitBytes` を保存する。永続レコードを読み出すたびに対応するzod/mini schemaで検証し、不正レコードは使用しない。不正なtile metadataは削除、不正なarea/settingsは安全な既定値と日本語エラー表示にする。

### 8.2 Wrapper

`database.ts` は以下だけを提供する薄いwrapperとする。

- DBをsingleton Promiseでopenする。
- `IDBRequest` をPromiseへ変換する。
- transaction完了・abortをPromiseで待つ。
- 複数Storeを同一transactionで更新するcallbackを提供する。
- `versionchange` 受信時はconnectionをcloseする。

汎用ORM、query builder、独自repository frameworkは作らない。

### 8.3 Repository操作

`tileMetadataRepository.ts`:

- get/put/delete metadata
- 複数tileの`lastAccessedAt`を1 transactionで更新
- `byLastAccessed`を昇順cursor走査し、`pinned=false`だけをGC候補として返す
- pinned/temporaryそれぞれの件数・`size`合計
- tileKeyに対するarea参照有無の確認

`offlineAreaRepository.ts`:

- area CRUD
- areaと対象tile参照/jobsの一括作成
- job状態とarea進捗の同一transaction更新
- area削除時の参照削除と、参照が0になったtileの`pinned=false`更新
- 起動時に `downloading` のareaを `paused` へ変更

Area作成時には全tileの `offlineAreaTiles` と `downloadJobs` を同じtransactionで保存する。これが「必要なタイル一覧」の永続データとなる。既存binaryとmetadataが整合しているtileはjobを`completed`、metadataを`pinned=true`にし、それ以外を`pending`にする。

## 9. OPFSタイルストレージ

`opfsTileStorage.ts` は `navigator.storage.getDirectory` の有無をfeature detectし、次を提供する。

```ts
interface TileBinaryStorage {
  isSupported(): boolean;
  read(tile: TileCoordinate): Promise<ArrayBuffer | undefined>;
  write(tile: TileCoordinate, data: ArrayBuffer): Promise<void>;
  exists(tile: TileCoordinate): Promise<boolean>;
  delete(tile: TileCoordinate): Promise<void>;
}
```

- 読み書き時に `tiles/source/z/x` directoryを必要な階層だけ取得・作成し、ファイル名を `{y}.png` とする。
- readでdirectory/fileがない `NotFoundError` はMISSとして `undefined` を返す。他の例外はstorage errorとして上位へ返す。
- write前にHTTP responseのvalidationを完了する。`createWritable({ keepExistingData: false })` へ全bytesを書き、`close()` 成功をcommitとみなす。write/close失敗時は既存metadataを更新しない。
- deleteのNotFoundは成功扱いにする。
- 空directoryの積極的な掃除や起動時全ファイル走査は行わない。

バイナリとmetadataの自己修復規則は次とする。

- metadataあり/binaryなし: アクセス時にmetadataを削除してMISSへ進む。
- binaryあり/metadataなし: binaryを読み、現在時刻、実size、`pinned=false` でmetadataをlazy作成してHITとして使う。
- 不正metadata/binaryあり: 不正metadataを削除後、同様に再構築する。

## 10. HTTP取得とレスポンス検証

`tileFetcher.ts` はタイルネットワーク取得だけを担当する。SWRは使用しない。

- `fetch(url, { signal, headers, cache: "no-store" })` を使う。
- 通常成功はstatus 200のみ。再検証では304も結果型として返す。
- Content-Typeはparametersを除去してlowercase化し、source定義の `image/png` または互換の `image/*` のうち許可した値と照合する。HTMLやJSONは拒否する。
- body長0は拒否する。`Content-Length` があれば0より大きいことと、実body長との一致を確認する。不一致なら保存・表示しない。
- `ETag`, `Last-Modified` を取得してmetadataへ保存する。
- 条件付き要求では既存値があるheaderだけを付ける。304はbodyを読まない。
- 412の場合に限り、条件headerなしのGETを一度だけ行う。serverが条件headerを無視して200を返す場合は通常の更新として扱う。
- HTTP error、timeout相当のAbort以外のnetwork errorは上位で分類できる独自errorへ変換する。技術詳細はdevelopment loggerだけへ出す。

同時数制御用 `Semaphore` は待機Promise、release、AbortSignalによる待機解除だけを持つ小さな実装にする。visible fetch用12、revalidation用2、offline download用6を別枠にし、表示要求がdownloadに占有されないようにする。

## 11. TileRepositoryとLocal Firstアルゴリズム

### 11.1 公開interface

`TileRepository.ts` に次だけを公開する。

```ts
interface TileRepository {
  getTile(request: TileRequest): Promise<TileResult>;
  downloadTile(
    request: TileRequest,
    options: DownloadOptions,
  ): Promise<TileResult>;
  deleteTile(key: TileKey): Promise<void>;
  flushAccessTimes(): Promise<void>;
}
```

### 11.2 通常表示 `getTile`

処理順を次に固定する。

1. tile keyを検証する。
2. OPFS対応時はbinaryを読む。同時にmetadataを読む。
3. binaryがあれば結果を`source: "local"`で即時返す。待つのはOPFS readだけであり、`lastAccessedAt`の永続化と再検証を待たない。
4. keyと現在時刻をaccess bufferへ記録する。5秒経過または100件到達で一括flushし、同じkeyは最新時刻へdeduplicateする。`pagehide` と `visibilitychange(hidden)` でもbest effort flushする。
5. `navigator.onLine` がtrueで、`now - lastCheckedAt >= 24h` ならrevalidationをfire-and-forgetで開始する。同じkeyの再検証Promiseがあれば追加しない。失敗は既存tileを維持してdevelopment logだけに記録する。
6. binaryがなければ不整合metadataを削除する。
7. offlineなら `TileUnavailableError("offline-miss")` をthrowする。
8. onlineならvisible semaphore下でnetwork GETを行う。同じkeyの前景取得はin-flight mapでdeduplicateする。
9. validな200 bodyを保持した状態で、OPFS対応時はbinary write、その成功後にmetadataの `pinned=false` putまで待つ。保存に失敗した場合はwarningを記録するが、すでに検証済みのnetwork bodyをMapLibreへ返す。保存成功・失敗のどちらでも同じnetwork bodyを返すため、永続化失敗を表示失敗へ波及させない。

`navigator.onLine` はfetchを試すかの初期判断だけに使い、true時の実到達性はfetch結果で判断する。

### 11.3 Background revalidation

- metadataのETag/Last-Modifiedを使って条件付きGETする。
- 304: binaryを変更せず、`lastCheckedAt=now` だけ更新する。
- 200: response検証後にbinaryを置換し、その成功後に`size`, `contentType`, `updatedAt`, `lastCheckedAt`, `etag`, `lastModified`を更新する。`createdAt`, `lastAccessedAt`, `pinned`は維持する。
- network/HTTP/validation/write error: binaryとmetadataを変更しない。次回アクセスで再試行可能なままにする。
- UIへ完了Toastを出さず、MapLibreの現在表示を強制reloadしない。更新版は次回tile要求から使う。

### 11.4 明示download `downloadTile`

- local binaryとvalid metadataがあり `forceRevalidate=false` の場合、network取得せずarea参照を確認して`pinned=true`にする。
- localがなくonlineならoffline semaphore下で取得、検証、OPFS write、metadata putを行い、その後にarea jobをcompletedにする。
- `forceRevalidate=true` はareaの「更新」操作用。localありなら条件付きGETし、304でもcompleted、200なら置換する。network失敗時は既存tileを壊さないが、その更新jobはfailedとする。
- localなし/offlineはdownload失敗としてjobをpendingのまま残し、areaをerrorにする。再開可能にする。
- pin設定、area参照、job completed、areaの`downloadedTileCount`更新は同一IndexedDB transactionで行う。

### 11.5 DeduplicationとAbort

in-flight registryは目的別ではなくtile key単位で、進行中のnetwork/write Promiseを共有する。ただし呼出元のAbortSignal一つで共有処理全体を中止しない。

- 各consumerの待機だけを自身のAbortSignalで解除する。
- 全consumerが離脱した時だけ共有fetchのAbortControllerをabortする。
- offline download consumerはMapLibre protocolのcancelで離脱しない。
- visible要求とoffline downloadが競合した場合、すでにnetwork処理中なら共有し、まだqueue待機中ならvisible priorityを優先する。

単純なconsumer count付きregistryで実装し、汎用タスクスケジューラにはしない。

## 12. MapLibre統合

### 12.1 custom protocol

`protocol.ts` でアプリ起動時に一度だけ `maplibregl.addProtocol("opfs-gsi", handler)` を登録する。HMRや再mountで二重登録しないmodule-level guardを置く。

- URL `opfs-gsi://std/{z}/{x}/{y}` をparseしてTileRequestへ変換する。
- handlerはTileRepositoryの `getTile` を呼び、MapLibreが要求するbinary responseを返す。
- protocol requestごとにAbortControllerを作り、MapLibreのcancel callbackでabortする。
- `TileUnavailableError` はtile単位の失敗として返し、アプリ全体のToastを連続表示しない。
- MapLibreの採用versionに対応する公式 `addProtocol` 型をそのまま使い、`any` や二重castで型を回避しない。

### 12.2 map生成

`createMap.ts` はcontainerと初期cameraを受け、次を設定する。

- raster source URL: `opfs-gsi://std/{z}/{x}/{y}`
- raster layer、source minzoom/maxzoom、tileSize 256
- attribution control
- built-in navigation controlのうちzoom buttonsのみ。独自の現在地・方角ボタンはReact overlayとして描画
- style load完了後に現在地source/layersを追加
- mountごとに1 map、unmountで `map.remove()` とevent listener解除
- `moveend` でcenter/zoom/bearing/pitchをmapStoreへ保存。高頻度moveイベントでZustand更新しない

MapPageは地図containerを最大化し、safe-areaを考慮した右側controlsと下部navigationを重ねる。

## 13. 現在地と方角

### 13.1 Geolocation

- 起動時にはpermission promptを出さない。
- 現在地ボタン初回押下で `watchPosition` を開始し、statusをrequestingにする。
- optionsは `{ enableHighAccuracy: true, maximumAge: 10_000, timeout: 15_000 }`。
- successでlatitude, longitude, accuracy, heading, speed, timestampをlocationStoreへ保存する。
- permission deniedはdenied、POSITION_UNAVAILABLE/TIMEOUTはunavailableとする。
- 初回のavailable時およびユーザーが現在地ボタンを再度押した時だけ現在地へcamera移動する。追跡中の毎更新で地図中心を強制しない。
- unmount/追跡停止時に `clearWatch` する。

### 13.2 現在地layer

MapLibre GeoJSON sourceを一つ使い、React componentを大量生成しない。

- accuracy circleは地理座標上のcircle polygonを十分な32点で計算する小さな純粋関数で生成する。
- current positionはcircle layer。
- headingはsymbol用の自前SVG arrow image、またはGeoJSON line/triangle layerで描画する。外部icon libraryは追加しない。
- 位置更新時は既存sourceの `setData` を使う。

### 13.3 Device Orientation

- `DeviceOrientationEvent` がなければunavailable。
- 静的 `requestPermission` が存在するiOS系では「方角を有効にする」ボタンのclick handler内で直接呼ぶ。granted以外はdenied。
- 許可後に `deviceorientationabsolute` が利用可能なら優先し、そうでなければ `deviceorientation` をlistenする。
- `webkitCompassHeading` が数値ならそれを使用する。それ以外はabsolute eventのalphaから `heading = (360 - alpha) % 360` を算出する。
- 値が有限数でないeventは無視する。
- listenerを二重登録せず、unmount時に解除する。

### 13.4 Heading統合

`heading.ts` の純粋関数でUI向けheadingを決める。

1. GPS `coords.heading` が有限数で、speedが1 m/s以上ならGPSを優先。
2. それ以外は利用可能なDevice Orientation headingを使用。
3. どちらもなければheadingなし。

Storeにはsourceも `"gps" | "orientation"` として保持し、表示layerはsourceを意識せず最終headingだけを受ける。

## 14. OfflineAreaとDownload Manager

### 14.1 作成Dialog

Map画面の「表示範囲を保存」からDialogを開き、次を表示・入力する。

- 名前。初期値は `オフライン地図 YYYY/MM/DD HH:mm`。trim後1〜50文字必須。
- 読み取り専用の現在bounds。
- 整数minZoom/maxZoom。sourceの0〜18内、min <= max。
- 対象タイル枚数。
- 推定容量。
- `navigator.storage.estimate()` のusage、quota、推定空き容量。API非対応時は「取得できません」。

確認Dialogを開いた時点のboundsをsnapshotし、地図移動で裏から値を変更しない。枚数が0、不正入力、OPFS非対応ではDownload buttonを無効化する。推定容量が空き容量を超える場合は警告し、開始buttonを無効化する。巨大範囲に別の恣意的上限は設けず、枚数と容量を明示してユーザー確認を必須にする。

### 14.2 Area作成

1. `crypto.randomUUID()` でidを作る。
2. `tileMath` で安定順のtile一覧を生成する。
3. status=pendingのarea、area参照、jobsを1 transactionで保存する。
4. area一覧へ反映後にDownload Managerを開始する。

同じbounds/nameの重複areaは許可する。tile binaryは共有され、参照だけが増える。

### 14.3 Download Manager

Download Managerはアプリ内singletonとし、同じareaを二重実行しない。

- 開始時にareaをdownloadingへ変更。
- `pending` と `failed` jobsを安定順で読み、同時6件で処理する。
- 成功ごとにjob completedとarea countをtransaction更新し、offlineStoreへ進捗通知する。
- network/HTTP/validation errorは1秒、3秒の固定backoffで最大2回再試行する。Abort、offline、quota errorは自動retryしない。
- retry後も失敗したjobはfailed、areaはerror、他の実行中jobは完了を待って新規投入を止める。
- 全job completedならareaをcompletedにする。
- pauseは新規job投入を停止し、専用AbortControllerで実行中download fetchをabortし、areaをpausedにする。completed jobは維持し、abortされたjobはpendingへ戻す。
- resumeはbinary/metadataを再確認し、整合する対象をcompleted/pinnedへ修復して残りだけを処理する。
- page load時にdownloadingだったareaはpausedへ正規化し、自動再開しない。
- `navigator.onLine=false` では開始・再開せず、再開可能な日本語メッセージを表示する。

### 14.4 更新

Offline detailの「更新」で全対象jobをpendingへ戻し、`forceRevalidate=true` でDownload Managerを動かす。304/valid 200はcompleted。個別失敗があればerrorにして再開可能とする。既存binaryは失敗時も利用可能であり削除しない。

### 14.5 削除

確認Dialog後に次のtransactionを行う。

1. areaの実行をpause/abortする。
2. areaに属するjobsとarea参照を削除する。
3. 各tileKeyの `byTileKey` indexで他area参照を確認する。
4. 参照0のtile metadataだけ `pinned=false` にする。
5. areaを削除する。

binaryとmetadata自体は残し通常キャッシュにする。削除途中に再実行しても壊れないよう、存在しないareaの削除は成功扱いにする。

## 15. Storage、Persistent Storage、GC

### 15.1 Persistent Storage

起動時はfeature detection後に `navigator.storage.persisted()` だけを呼ぶ。`persist()` はSettings画面の「ストレージを保護」button、または最初のOfflineArea download確定clickというユーザー操作内で要求する。結果を次で表示する。

- true: `ストレージ保護: 有効`
- false/拒否: `ストレージ保護: 未保証`
- API非対応: `ストレージ保護: 非対応`

falseでも機能を停止しない。

### 15.2 Storage statistics

`storageService.ts` が次を一つの結果に集約する。

- Downloaded Maps: `pinned=true` metadataのsize合計
- Temporary Cache: `pinned=false` metadataのsize合計
- Total: 上記合計
- Browser usage/quota: `navigator.storage.estimate()` の値
- 保護状態

この統計取得にはSWRを使用し、keyを `storage-statistics`、画面focus時とdownload/GC完了時にmutateする。タイル単位の進捗更新ごとには全件再集計しない。

### 15.3 通常キャッシュGC

通常のnetwork tile保存前にsoft limit超過が見込まれる場合だけGCを実行する。目標は `currentTemporaryBytes + incomingBytes <= effectiveLimit`。

1. `effectiveLimit = min(configuredLimit, quota*0.2)`。quota不明ならconfiguredLimit。
2. `byLastAccessed` indexを昇順走査し、`pinned=true` は読み飛ばす。
3. 最初に見つかったunpinned tileのbinaryを削除する。
4. binary削除成功またはNotFound後にmetadataを削除する。
5. 目標容量まで繰り返す。

pinned tileはcursor候補にも含めない。GC失敗時にpinnedを消さない。通常保存がquota errorになった場合はGCを一度行い、そのtileの保存を一度だけretryする。retry失敗でも取得済みnetwork tileの表示は行い、永続保存失敗として扱う。

Settingsの「一時キャッシュを削除」は確認後、同じ列挙処理ですべてのunpinned binary/metadataを削除する。OfflineAreaは変化させない。進捗中のtileと競合しないようtile key registryを通す。

明示download開始前は必要容量と空き容量を比較する。途中のquota errorではareaをerrorで停止し、「一時キャッシュを削除するか保存範囲を小さくしてください」と表示する。pinned tileを自動削除しない。

## 16. Zustand Store

Storeにはserializableな表示状態と操作だけを置き、MapLibre instance、IDB connection、OPFS handle、AbortController、Download Managerを格納しない。

- `mapStore`: longitude, latitude, zoom, bearing, pitchとcamera更新。
- `locationStore`: status、coords、accuracy、GPS heading/speed/timestamp、tracking flag。
- `orientationStore`: status、heading、absolute。
- `networkStore`: `navigator.onLine` 初期値、online/offline eventで更新。
- `offlineStore`: area summary一覧、実行中area id、表示用進捗、load/error状態。永続の正本はIndexedDB。
- `settingsStore`: cache limitとロード状態。永続の正本はIndexedDB。
- `uiStore`: Toast queueと開いているDialogに必要な最小状態。

`useNetworkEvents` はApp rootで一度だけmountし、listener cleanupを行う。onlineへ戻ってもarea downloadを勝手に再開しない。

## 19. エラー分類とログ

`errors.ts` に `TileUnavailableError`, `StorageUnavailableError`, `QuotaExceededAppError`, `TileValidationError` を定義し、UIはinstance/typeから日本語文言へ変換する。生のexception messageやHTTP statusを本番UIに出さない。

ユーザー文言は少なくとも次を統一する。

- offline miss: `オフラインで、この地域の地図が保存されていません。`（連続Toastにはせず必要な状態表示だけ）
- download offline: `オフラインのためダウンロードを開始できません。`
- quota: `ストレージの空き容量が不足しています。一時キャッシュを削除するか、保存範囲を小さくしてください。`
- permission denied: 現在地/方角ごとに設定から許可できる旨を表示。
- unsupported: API名ではなく利用できない機能名を表示。

`logger.ts` はdevelopment時だけdebug/infoをconsoleへ出し、warn/errorもtile単位で大量反復しないよう呼出箇所を限定する。外部logging/analyticsを導入せず、位置情報を送信・永続化しない。

### 20.2 cache/repository

fake OPFS、fake metadata repository、mock fetch、fake clockを用いて検証する。

- local HITはfetch完了を待たずlocal bytesを返す。
- local HIT + offlineはfetchしない。
- MISS + offlineは明示error。
- MISS + onlineはfetch、validation、binary、metadataの順で保存。
- network成功/storage失敗でもnetwork bytesを返す。
- invalid status/content type/empty bodyは保存しない。
- metadataあり/binaryなしを削除してnetwork fallback。
- binaryあり/metadataなしをlazy修復。
- 24時間未満はrevalidateしない。境界以上で行う。
- 304はlastCheckedAtだけ、200はbinary/headersを更新。
- revalidation失敗で既存binary/metadataを維持。
- 同じtileの同時要求がfetch一回。
- consumer一つのabortで他consumerを止めない。
- access bufferが時間/件数/pagehideでbatch flushし、keyをdeduplicate。

### 20.3 OfflineArea/download

- area作成でarea/ref/job件数がtile計算結果と一致。
- 既存cache tileは再取得せずcompleted/pinnedになる。
- 6件を超えて同時fetchしない。
- 成功ごとにcountが増え、全成功でcompleted。
- pauseで新規投入停止、active abort、pending維持。
- reload recoveryでdownloadingがpausedになる。
- resumeでcompletedを再取得せずmissingだけ取得。
- retryは最大2回と固定backoff。
- quota/offlineでerrorになり再開可能。
- updateの304/200/失敗。
- 共有tileを持つareaを片方削除してもpinned=true。
- 最後のarea削除でpinned=false、binaryは残る。

- unpinnedをlastAccessedAt昇順で削除。
- limit到達で停止。
- pinnedを一切削除しない。
- binary削除後にmetadata削除。
- NotFound binaryのmetadataを掃除。
- quotaを考慮したeffective limit。
- cache clearでarea/pinnedが変化しない。
- storage statisticsの分類と合計。

3. storage保護要求と一時cache clear UIを実装する。

完了条件: pinnedを保持したままoldest temporary cacheだけを削除し、Settingsの内訳が操作後に更新される。

### Phase 7: 統合仕上げ

1. 日本語エラー、Toast頻度、unsupported state、accessibilityを確認する。
2. PWA offline cold startとtile Cache Storage非使用を確認する。
3. production logging、position非永続化、attributionを確認する。
4. 全品質commandと手動確認マトリクスを実行する。

完了条件: 第3章の完成条件をすべて満たし、未確認の実機項目だけが明記された状態になる。

## 22. 実装時の変更規律

- 各Phaseは必要なファイルだけを追加・変更し、後続Phaseの将来抽象化を先に作らない。
- `any`、広範囲なtype assertion、無言のcatch、UIからの直接storage/fetch呼出しを認めない。
- 要件外のライブラリや機能を追加する必要が生じた場合は、実装を進める前に理由と代替案を提示して確認する。
- 国土地理院タイルの公開運用前には、実装時点の最新利用条件を確認する。これはコード完成とは別のリリース必須確認項目としてREADMEまたはrelease checklistへ残す。
- ブラウザーAPI差異に遭遇した場合、Cache Storageへのtile退避やlocalStorageへのbinary保存など別責務のfallbackを追加しない。feature detection結果をUIへ反映する。
- 性能問題が計測されるまではWeb Worker、OPFS sharding、source別/zoom別高度統計、E2E frameworkを追加しない。
